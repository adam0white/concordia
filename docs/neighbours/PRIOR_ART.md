# Prior art and fork choice

On 2026-10-16 we sampled the 100 newest and 100 most-starred public Concordia forks, compared default branches with upstream `6fbfbc58`, and read selected source and README files. Fifteen of the newest sample had unique default-branch commits. We did not install or run those forks. This is a bounded source survey, not a reliability benchmark.

| Reference | Useful idea | Why we did not inherit it as the base |
| --- | --- | --- |
| [concordia-memory](https://github.com/1664178416/concordia-memory) | Programmatic social outcomes, memory controls, checkpoint/replay | Its controlled community is separate from native Concordia integration. |
| [vecnode](https://github.com/vecnode/concordia) | Sweeps, aggregation, engine routing | Older base; source documents action-order limits on bit reproducibility. |
| [PGlynn](https://github.com/PGlynn/concordia) | Real browser inspector, run controls and checkpoint UI | Dating-show specific; external scenario data needed. |
| [Bruce-anle](https://github.com/Bruce-anle/concordia) | Strict restore and roster checks | Focused older patch; compare against current upstream before reuse. |
| [dgxy2002](https://github.com/dgxy2002/concordia) | Frozen rules, request logs and explicit audits | Domain benchmark rather than a general watchable town. |

We created a proper GitHub fork of current upstream. No code from the other forks was copied. Their ideas informed replay, explicit physical outcomes, experiment controls and the optional inspector. Preserve license and source provenance if we later port a specific patch.

Early design consultation selected one shared history, competing ordinary obligations and a few scarce interventions. The wildcard critique warned that a dashboard can become an operations console before there is a place worth watching. The first source-unread watch confirmed that risk. Follow-up work therefore prioritized meaningful received information, physical teaching and visible consequences over more metrics.
